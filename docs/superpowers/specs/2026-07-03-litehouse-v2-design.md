# Litehouse v2 Design

**Date:** 2026-07-03
**Status:** Draft for review

## One-line vision

Self-hosted, single-server platform for SQLite apps: `lh create` once, `git push` to deploy forever. The server only *runs* things — GitHub builds, GHCR stores images, S3 stores backups.

## Guiding principle: "drunk proof"

Creating and deploying a new app late at night must require no thinking:

```
lh create myapp --repo dan/myapp   # generates workflow, sets secrets, registers app
git push                           # builds on GitHub, deploys to server
```

Everything else (SSL, subdomain, backups, recovery) is automatic.

## Architecture

Four responsibilities, four owners:

| Concern | Owner |
|---|---|
| Build | GitHub Actions |
| Image storage | GHCR (`ghcr.io/<user>/<app>`) |
| Run + route | The server (litehouse-server + Caddy containers) |
| Data backup | Daily upload to S3 |

### Components on the server

1. **litehouse-server container** (Rust, single binary):
   - Admin API (used by CLI and web UI)
   - Deploy hook: `POST /hooks/deploy` (bearer token) → `docker pull` from GHCR → recreate container → sync Caddy
   - Web admin UI (Htmx + Tailwind, served from the same binary)
   - Daily backup job (built-in scheduler, no host cron)
   - SQLite state DB (`litehouse.db`): apps, deploys, tokens, settings
2. **Caddy container**: wildcard subdomain routing (`{app}.litehouse.run`), automatic HTTPS via Let's Encrypt. Config synced over Caddy admin API (keep v1 mechanism).
3. **App containers**: one per app, named `{app}-container`, each with a Docker volume for data (SQLite lives on the volume).

### Deploy flow

1. `git push` to GitHub
2. Repo workflow (generated by `lh create`) builds the image, pushes `ghcr.io/<user>/<app>:latest` + `:<sha>` (uses built-in `GITHUB_TOKEN`, no extra secret for GHCR)
3. Workflow calls `POST https://admin.litehouse.run/hooks/deploy` with `{app, image, sha}` and a per-app bearer token (stored as a repo secret by `lh create`)
4. Server pulls the image, recreates the container with env vars + volume, syncs Caddy, records the deploy

Local escape hatch: `lh deploy myapp` builds locally, pushes to GHCR, calls the same hook. Same path, one code path on the server.

### `lh create` (the drunk-proof command)

Given `lh create myapp --repo dan/myapp` (or run inside a repo checkout, inferring the remote):

1. Registers the app on the server (API call); server mints a deploy token
2. Commits `.github/workflows/litehouse-deploy.yml` to the repo (complete self-contained template, ~25 lines: docker build → push GHCR → curl deploy hook)
3. Sets the `LITEHOUSE_DEPLOY_TOKEN` repo secret via the GitHub API (reuse existing `src/github` client/oauth code)
4. Prints the app URL

Requires a one-time `lh github login` (device-flow OAuth — already exists in v1 code).

### Backups (no Litestream, no Restic)

Daily job inside litehouse-server:

1. For each app volume: `sqlite3 <db> "VACUUM INTO '/backup/db.sqlite'"` for a consistent snapshot of every `*.db`/`*.sqlite*` file, plus a tar of the rest of the volume
2. Also snapshot `litehouse.db` itself (the app registry — required for recovery)
3. Upload to `s3://<bucket>/litehouse/<app>/<date>.tar.gz` (Rust S3 client, S3-compatible endpoints supported)
4. Retention: keep last 14 daily backups, prune older
5. `lh backup run` triggers it manually; UI shows last-backup status per app

S3 credentials + bucket collected by `lh server init`, stored in server config.

### Disaster recovery

Fresh droplet to running apps:

1. `lh server init` on the new node (installs Docker, starts litehouse-server + Caddy; asks for S3 credentials)
2. `lh restore` — pulls the latest `litehouse.db` snapshot from S3 → now the server knows every app, image ref, env vars, and deploy tokens
3. For each app: `docker pull` from GHCR (server holds one GHCR read token, set during init), restore the volume from the latest S3 backup, start container
4. Point DNS at the new IP (wildcard record — one Cloudflare change, automatable later)

Images come from GHCR, data comes from S3, state comes from S3. Nothing on the server is precious.

## What gets deleted from v1

- `src/litestream.rs` (~1000 lines) and all Litestream config/volume plumbing
- On-server build path: `src/commands/build.rs` server-side flow, `src/git.rs` clone/pull, build directories
- `remote` concept (git remotes tracked in DB) — replaced by `repo` field on the app plus the generated workflow
- `reconciler.rs` if its only job was build/state reconciliation (re-evaluate; keep only container-state sync if the UI needs it)
- `build` DB table → replaced by a simpler `deploy` table (app_id, image, sha, deployed_at, status)

## What gets kept

- Docker integration (`src/docker.rs`, Bollard) — minus build functions
- Caddy management (`src/caddy.rs`) as-is
- Client/server API structure, CLI skeleton, SQLite state DB + migrations approach
- GitHub OAuth/device-flow code (`src/github/`) — repurposed for secret-setting and workflow commit
- Webhook signature/token verification patterns (`src/webhook/`) — adapted for the deploy hook
- Admin SPA scaffolding (`src/admin_spa.rs`) as the base for the Htmx UI
- `lh server init` idempotent install stages

## Error handling

- Deploy hook failures return structured errors to the workflow (visible in the Actions log — that's where a drunk Dan will look)
- Failed deploys keep the previous container running (pull + create new before removing old; roll back on start failure)
- Backup failures surface in UI + `lh status`; a missed backup never blocks deploys

## Testing

- Keep the Docker integration-test pattern (real containers) for run/stop/deploy-hook paths
- Workflow template gets a golden-file test
- Backup/restore round-trip test against MinIO in a container

## Addendum: further simplifications (approved 2026-07-03)

Dan is not attached to v1 patterns, so v2 also abandons:

- **JWT/user/org auth → single admin token.** One operator, one server. `lh server init` generates a random token; the server stores its SHA-256 hash; CLI and browser present it (bearer header or cookie). Deletes `src/auth/` (JWT, argon2, refresh tokens), `user`/`organization`/`organization_member`/`refresh_token` tables and models.
- **Elm SPA → Askama + HTMX server-rendered UI.** Deletes `assets/` (Elm project), `compile-assets.sh`, rust-embed. UI is templates in the server binary.
- **message_bus + SSE + reconciler deleted.** Logs served by plain HTTP streaming; container liveness handled by Docker restart policies plus a startup sync; no in-process pub/sub.
- **Server-side GitHub connection removed.** The device-flow token lives in the *client* config (`lh github login` runs locally); the server never talks to the GitHub API — it only pulls from GHCR with a read-only token.
- **litehouse-server image from GHCR.** The release workflow publishes `ghcr.io/danbruder/litehouse` — the install no longer builds an image on the droplet.
- **Domain:** parametrized; acceptance environment uses `*.s.danbruder.com`.

## Agent-friendly operation (first-class requirement)

Claude (or any coding agent) must be able to take an app from source to running URL without a human in the loop:

- **Non-interactive everywhere.** Every command works with flags/env vars only — no prompts. GitHub auth prefers `GITHUB_TOKEN` env (or `gh auth token`) over device flow; device flow is the human fallback.
- **Machine-readable output.** `--json` on all read commands (`lh status`, `lh apps`, `lh deploys`); meaningful exit codes.
- **Verifiable outcomes.** `lh create` prints the app URL; `lh deploys <app> --wait` blocks until the in-flight deploy succeeds or fails and exits accordingly, so an agent can `git push && lh deploys myapp --wait && curl $URL`.
- **Idempotent commands.** Re-running `lh create` on an existing app updates the workflow/secret instead of erroring.

## Out of scope for v2

- Multi-server, zero-downtime blue/green, metrics/alerting
- Automatic Cloudflare DNS (Phase 3 as before)
- Postgres/other databases
